# Руководство по квизу PainHelp

## Назначение документа
Этот документ описывает:
- какие возможности есть у текущего квиз-движка,
- как устроены сценарии,
- как создавать новые квизы,
- как безопасно редактировать существующие,
- как запускать A/B/C варианты и интерпретировать результат.

## 1. Что умеет текущий квиз

### 1.1 Пользовательский флоу
Квиз проходит по шагам:
1. Hero-экран (заголовок, подзаголовок, trust badges, кнопка старта).
2. Вопросы по сценарию.
3. Экран email.
4. Расчет результата.
5. Показ результата и CTA.
6. Отправка данных в CRM.

### 1.2 Data-driven архитектура
Поведение квиза определяется JSON-сценарием без изменений JS-кода, если соблюдается схема.

### 1.3 Поддержка произвольного числа уровней скоринга
Скоринг больше не ограничен тремя категориями. Можно задавать 3, 5, 7 и более уровней через блок scoring.

### 1.4 Ранний выход в финал при score = 0
Если выбран вариант ответа с весом 0, квиз сразу завершает вопросы и переходит к финальному этапу (экран email/результат).

### 1.5 Условные флаги (диагностические признаки)
Поддерживаются флаги на уровне вопроса:
- chronic_if_gte_index + chronic_threshold
- failed_treatment_if_value + failed_treatment_value

Флаги влияют на итоговые поля CRM и визуальные отметки в результате.

### 1.6 CRM-интеграция
Квиз умеет отправлять лид в Bitrix24 webhook:
- email,
- ответы на вопросы с crm_field,
- итоговый балл,
- уровень результата,
- флаги,
- служебные поля (source, дата).

Если webhook пустой или placeholder, работает демо-режим без POST.

### 1.7 Поддержка нескольких сценариев
Сценарий выбирается через query-параметр quiz:
- ?quiz=pain-v1
- ?quiz=pain-v1_strict_2608_001
- ?quiz=pain-v1_growth_2608_001


## 2. Ключевые файлы в проекте

- Основной квиз: 1st-pain-quiz-styled.html
- Сценарии: scenarios/*.json
- Конструктор: quiz-editor/index.html, quiz-editor/app.js, quiz-editor/style.css
- API/обработчики: api/*, server.js


## 3. Схема JSON-сценария

Минимальная структура:

```json
{
  "meta": { },
  "questions": [ ],
  "scoring": { },
  "crm_fields": { }
}
```

### 3.1 meta
Обязательные/часто используемые поля:
- title
- subtitle
- trust_badges (массив)
- cta_start
- webhook
- source_label
- email_title
- email_subtitle
- email_fear

### 3.2 questions
Массив вопросов в порядке показа.

Поля вопроса:
- id: стабильный машинный идентификатор (строка)
- crm_field: поле Bitrix24 (опционально, но обычно нужно)
- text: текст вопроса
- options: массив вариантов

Поля варианта:
- label: что видит пользователь
- value: что пишется в ответы/CRM
- score: вес для суммарного балла

Поля флагов (опционально):
- flag: chronic_if_gte_index
- chronic_threshold: порог индекса выбранной опции

или

- flag: failed_treatment_if_value
- failed_treatment_value: значение value, активирующее флаг

### 3.3 scoring
Объект уровней. Ключи могут быть любыми: level_1, level_2, low, medium, high и т.д.

Для каждого уровня:
- max: верхняя граница балла включительно
- title: заголовок результата
- text: описание результата
- cta: массив кнопок (рекомендуется объекты { text, url })

Пример:

```json
"scoring": {
  "level_1": {
    "max": 2,
    "title": "Низкий риск",
    "text": "...",
    "cta": [
      { "text": "Подробнее", "url": "#" }
    ]
  },
  "level_2": {
    "max": 6,
    "title": "Умеренный риск",
    "text": "...",
    "cta": [
      { "text": "Консультация", "url": "#" }
    ]
  }
}
```

### 3.4 crm_fields
Маппинг итоговых полей:
- score
- result
- is_chronic
- failed_treatment
- source


## 4. Правила корректного скоринга

1. Уровни должны покрывать полный ожидаемый диапазон баллов.
2. max должны расти монотонно.
3. Последний уровень должен включать максимум шкалы.
4. Если используется ранний выход score = 0, учитывайте, что часть пользователей не дойдет до части вопросов.

Рекомендуем перед выпуском вручную проверить:
- минимально возможный балл,
- максимально возможный балл,
- несколько граничных значений (ровно на max уровней).


## 5. Создание нового квиза (пошагово)

### Способ A: через копию сценария
1. Скопировать существующий JSON из scenarios/.
2. Переименовать файл по версии, например:
   - pain-v1_newidea_2608_001.json
3. Обновить meta.source_label под аналитику.
4. Отредактировать вопросы/ответы.
5. Отредактировать scoring.
6. Проверить crm_fields.
7. Запустить локально и открыть:
   - /1st-pain-quiz-styled.html?quiz=имя_без_.json

### Способ B: через конструктор
1. Открыть quiz-editor/index.html.
2. Внести изменения в Meta, Questions, Scoring, CRM.
3. Проверить вкладку Quiz Preview.
4. Экспортировать JSON.
5. Сохранить файл в scenarios/ по схеме версий.
6. Протестировать через query-параметр quiz.


## 6. Редактирование существующего квиза

1. Не редактировать прод-файл без версии.
2. Делать новую версию файла с суффиксом.
3. Сохранять id вопросов стабильными, если нужно сравнение исторических данных в CRM.
4. Если меняете value вариантов, учтите, что это изменит данные в CRM и аналитику.
5. При изменении scoring убедиться, что max-границы корректны.


## 7. Подход к версионированию сценариев

Рекомендуемый формат имени:
- pain-v1_<variant>_2608_001.json

Где:
- 2608 = август 2026
- 001 = версия внутри месяца

Примеры:
- pain-v1_baseline_2608_001.json
- pain-v1_strict_2608_001.json
- pain-v1_growth_2608_001.json


## 8. A/B/C сценарии

### Baseline
Контрольная версия для сравнения.

### Strict
Более ранний выход в высокие уровни риска.

### Growth
Более мягкий переход к высоким уровням, акцент на вовлечение.

### Что сравнивать
1. Распределение по уровням.
2. Конверсия в CTA/консультацию.
3. Доля раннего выхода по score = 0.
4. Качество лидов по source_label.


## 9. Как выбрать сценарий при запуске

Через URL параметр quiz:
- /1st-pain-quiz-styled.html?quiz=pain-v1_baseline_2608_001
- /1st-pain-quiz-styled.html?quiz=pain-v1_strict_2608_001
- /1st-pain-quiz-styled.html?quiz=pain-v1_growth_2608_001


## 10. Чеклист перед публикацией

1. JSON валиден.
2. У каждого вопроса уникальный id.
3. У options есть label/value/score.
4. scoring покрывает диапазон баллов.
5. Проверены граничные значения уровней.
6. Проверен ранний выход при score = 0.
7. Проверена отправка в CRM (или корректный демо-режим).
8. source_label уникален и понятен для аналитики.


## 11. Частые ошибки

1. Несортированные или конфликтующие max в scoring.
2. Дублирующиеся id вопросов.
3. Изменение value без учета CRM-отчетов.
4. Пустой webhook в проде.
5. Забыли обновить source_label при новой версии.


## 12. Быстрый FAQ

### Какой сценарий грузится по умолчанию в конструкторе?
Конструктор сначала берет сохраненное состояние, затем внешний load-пейлоад, и только если их нет, использует встроенный DEFAULT_JSON.

### Нужно ли менять код для 7 уровней?
Нет. Текущая версия поддерживает произвольное число уровней в scoring.

### Можно ли делать старые low/medium/high?
Да. Старый формат поддерживается.


## 13. Рекомендации по безопасным изменениям

1. Меняйте только один фактор за итерацию (вопросы или пороги, но не все сразу).
2. Для каждой гипотезы заводите отдельный файл сценария.
3. Сохраняйте baseline неизменным до конца цикла сравнения.
4. Фиксируйте дату и версию в имени файла.
