# Руководство по квизу PainHelp

## Назначение документа

Этот документ описывает:
- как устроен текущий квиз-движок,
- какая структура сценария считается корректной,
- как работают флаги и скоринг,
- какой список CRM-полей является каноническим,
- как выбирать и обновлять сценарии безопасно.

---

## 1. Что умеет текущий квиз

### 1.1 Пользовательский флоу

Квиз проходит по шагам:
1. Hero-экран: заголовок, подзаголовок, trust badges, кнопка старта.
2. Вопросы из сценария.
3. Экран email.
4. Расчёт результата.
5. Показ результата и CTA.
6. Отправка данных в CRM, если webhook настроен.

### 1.2 Data-driven архитектура

Поведение квиза определяется JSON-сценарием. При корректной схеме код движка почти не меняется.

### 1.3 Поддержка произвольного числа уровней скоринга

Скоринг не ограничен тремя уровнями. В одном сценарии может быть любое число уровней: low/medium/high или custom keys вроде `level_1`, `level_2`, `level_3`.

### 1.4 Ранний выход в финал при score = 0

Если выбран ответ с `score: 0`, квиз может завершиться раньше и перевести пользователя на финальный экран без дополнительных вопросов.

### 1.5 Условные флаги

Поддерживаются флаги:
- `chronic_if_gte_index` + `chronic_threshold`
- `failed_treatment_if_value` + `failed_treatment_value`

Эти флаги влияют на итоговые поля CRM и на визуальные маркеры в результате.

### 1.6 CRM-интеграция

Квиз умеет отправлять в Bitrix24:
- email пользователя,
- ответы по каждому `crm_field`,
- итоговый score,
- итоговый текст результата,
- флаги `is_chronic` и `failed_treatment`,
- `source` и JSON ответов.

Если webhook пустой или placeholder, движок работает в demo mode без POST.

### 1.7 Поддержка сценариев

Сценарий выбирается через query-параметр `quiz`:

```text
?quiz=pain-v1_growth_2608_001
```

Актуальная основная версия хранится в [scenarios/pain-v1_growth_2608_001.json](scenarios/pain-v1_growth_2608_001.json).

## 3. Каноническая схема CRM-полей

Это финальный проверенный список полей, который должен использоваться в сценариях:

- `score` → `UF_CRM_1777993552`
- `result` → `UF_CRM_1777993608`
- `is_chronic` → `UF_CRM_1777993788`
- `failed_treatment` → `UF_CRM_1777993848`
- `source` → `UF_CRM_1777993881`
- `answers_json` → `UF_CRM_1786729063`

### Важные правила

1. `result` должен содержать человекочитаемый текст результата, например:
   - "Серьёзных признаков не выявлено"
   - "Боль требует внимания"
   - "Рекомендуем обратиться к специалисту"
2. `answers_json` — это единственное поле для JSON ответов пользователя.
4. Не добавляйте свободные текстовые поля в CRM, если поле уже описано в каноническом списке.

## 4. Схема JSON-сценария

Минимальная структура:

```json
{
  "meta": {},
  "questions": [],
  "scoring": {},
  "crm_fields": {}
}
```

### 4.1 meta

Обязательные или часто используемые поля:

- `title`
- `subtitle`
- `trust_badges` (массив)
- `cta_start`
- `source_label`
- `email_title`
- `email_subtitle`
- `email_fear`

### 4.2 questions

Массив вопросов в порядке показа.

Поля вопроса:

- `id`: стабильный машинный идентификатор (строка)
- `crm_field`: поле Bitrix24 для ответа пользователя
- `text`: текст вопроса
- `options`: массив вариантов
- `flag`: необязательно, один из допустимых флагов

Поля варианта:

- `label`: текст, который видит пользователь
- `value`: служебное значение, которое записывается в ответы / CRM
- `score`: числовой вес для суммарного балла

Пример:

```json
{
  "id": "pain_duration",
  "crm_field": "UF_CRM_1777993660",
  "text": "Как давно появилась боль?",
  "flag": "chronic_if_gte_index",
  "chronic_threshold": 2,
  "options": [
    { "label": "Несколько дней", "value": "short", "score": 0 },
    { "label": "Несколько недель", "value": "weeks", "score": 1 },
    { "label": "Несколько месяцев", "value": "months", "score": 2 },
    { "label": "Более 6 месяцев", "value": "chronic", "score": 4 }
  ]
}
```

### 4.3 scoring

Объект уровней. Ключи могут быть любыми: `low`, `medium`, `high` или `level_1`, `level_2`, `level_3`.

Для каждого уровня:

- `max`: верхняя граница балла включительно
- `title`: заголовок результата
- `text`: описание результата
- `cta`: массив кнопок `{ text, url }`

Пример:

```json
"scoring": {
  "low": {
    "max": 3,
    "title": "Серьёзных признаков не выявлено",
    "text": "Судя по вашим ответам, боль пока не выглядит хронической.",
    "cta": [
      { "text": "Читать полезные материалы", "url": "" }
    ]
  },
  "medium": {
    "max": 7,
    "title": "Боль требует внимания",
    "text": "Некоторые ответы могут указывать на развитие хронической боли.",
    "cta": [
      { "text": "Получить консультацию", "url": "" }
    ]
  },
  "high": {
    "max": 99,
    "title": "Рекомендуем обратиться к специалисту",
    "text": "Ваши ответы указывают на высокую вероятность хронической боли.",
    "cta": [
      { "text": "Записаться на консультацию", "url": "" }
    ]
  }
}
```

### 4.4 crm_fields

```json
"crm_fields": {
  "score": "UF_CRM_1777993552",
  "result": "UF_CRM_1777993608",
  "is_chronic": "UF_CRM_1777993788",
  "failed_treatment": "UF_CRM_1777993848",
  "source": "UF_CRM_1777993881",
  "answers_json": "UF_CRM_1786729063"
}
```

## 5. Флаги CRM

### `chronic_if_gte_index`

Ставит `is_chronic = Y`, если индекс выбранного варианта больше либо равен `chronic_threshold`.

```json
{
  "flag": "chronic_if_gte_index",
  "chronic_threshold": 2
}
```

### `failed_treatment_if_value`

Ставит `failed_treatment = Y`, если `value` выбранного варианта совпадает с `failed_treatment_value`.

```json
{
  "flag": "failed_treatment_if_value",
  "failed_treatment_value": "no_result"
}
```

---

## 6. Правила корректного скоринга

1. Уровни должны покрывать полный диапазон возможных баллов.
2. `max` должны расти монотонно.
3. Последний уровень должен закрывать максимальный диапазон.
4. При раннем выходе по `score = 0` нужно проверять, что пользователь не теряет финальный результат.
5. В `result` должно быть человекочитаемое название результата, а не технический id категории.

## 7. Создание нового квиза

### Способ A: через копию сценария

1. Скопировать существующий JSON из [scenarios](scenarios).
2. Переименовать файл по версии, например:
   - `pain-v1_growth_2608_002.json`
3. Обновить `meta.source_label`.
4. Отредактировать вопросы, варианты и флаги.
5. Проверить `scoring` и `crm_fields`.
6. Подключить через `?quiz=...`.

### Способ B: через конструктор

1. Открыть [quiz-editor/index.html](quiz-editor/index.html).
2. Заполнить Meta, Questions, Scoring, CRM.
3. Проверить предпросмотр.
4. Экспортировать JSON.
5. Сохранить файл в [scenarios](scenarios).
6. Проверить в браузере по URL с `?quiz=...`.

## 10. Чеклист перед релизом

1. JSON валиден.
2. Все `id` уникальны.
3. У каждого варианта есть `label`, `value` и `score`.
4. `scoring` покрывает весь диапазон возможных значений.
5. Для каждого финального поля указано корректное Bitrix-поле.
6. `result` хранит итоговый текст результата.
7. Проверен demo mode и проверка вебхука.
8. `source_label` понятен для аналитики.

---

## 11. Частые ошибки

1. Смешение raw category id с текстом результата.
2. Дублирование поля `answers_json` в разных местах конфигурации.
3. Отсутствие `crm_fields.answers_json` в маппинге.
4. Неправильный `source_label` для кампании/канала.
5. Несогласованные границы `max` в scoring.

## 12. Быстрый FAQ

### Почему `result` не равен `low`/`medium`/`high`?

Потому что в этой архитектуре результатом в CRM считается человекочитаемый текст, который формируется из выбранного уровня результата.

### Почему нет отдельного поля для JSON сценария?

Потому что в текущей схеме есть одно поле `answers_json`, которое фиксируется как `UF_CRM_1786729063`.

### Какие сценарии следует использовать в продакшене?

Используйте только актуальную версию, которая лежит в [scenarios](scenarios), и выбирайте её через `?quiz=...`.

### Какой сценарий грузится по умолчанию в конструкторе?
Конструктор сначала берет сохраненное состояние, затем внешний load-пейлоад, и только если их нет, использует встроенный DEFAULT_JSON.

### Нужно ли менять код для 7 уровней?
Нет. Текущая версия поддерживает произвольное число уровней в scoring.

### Можно ли делать старые low/medium/high?
Да. Старый формат поддерживается.


## 13. Рекомендации по безопасным изменениям

1. Меняйте только один фактор за итерацию (вопросы или пороги, но не все сразу).
2. Для каждой гипотезы заводите отдельный файл сценария.
3. Сохраняйте baseline неизменным до конца цикла сравнения.
4. Фиксируйте дату и версию в имени файла.
